# 3. O fluxo real: de frase para tensor de embeddings

Até agora falamos de "uma palavra vira um vetor". Mas na prática, o que entra num modelo não é uma palavra isolada — é uma **frase inteira**, e ela passa por um fluxo com formatos (shapes) bem específicos. Vamos destrinchar.

## 3.1 O ponto de partida: a frase tokenizada

Antes do embedding, a frase é quebrada em tokens (aproximadamente palavras/pedaços de palavras) e cada token vira um número (um ID, tipo um índice num dicionário gigante).

```
"o cachorro correu muito"
        ↓ tokenização
[o, cachorro, correu, muito]
        ↓ vira IDs
[15, 342, 891, 27]
```

Isso é um vetor com **shape (1, 4)**:
- `1` = batch (estamos processando 1 frase por vez)
- `4` = número de tokens (palavras) na frase

Se fossem 10 tokens, seria `(1, 10)`. Repare: nesse ponto, cada posição ainda é só **um número** (um ID), não um vetor de significado ainda.

> Para entender melhor sobre tokenização veja: https://github.com/tevoshw/tokenization

## 3.2 A camada de embedding: onde o `(1, 10)` vira `(1, 10, X)`

Agora entra a camada de embedding. Ela funciona como uma tabela gigante de consulta (lookup table): para cada ID de token, ela busca a linha correspondente nessa tabela, e essa linha é o vetor de embedding daquele token.

```
ID 15  (o)        → [0.02, -0.11, 0.44, ..., 0.09]   # X números
ID 342 (cachorro) → [0.12, -0.44, 0.03, ..., 0.91]   # X números
ID 891 (correu)   → [0.55, 0.08, -0.29, ..., 0.14]   # X números
ID 27  (muito)    → [-0.19, 0.33, 0.61, ..., 0.02]   # X números
```

Cada token que era **um número** vira **uma linha de X números** (X = a dimensão do embedding, tipo 384 ou 768). Fazendo isso pra todos os 10 tokens da frase, o shape vira:

$$(1, 10) \rightarrow (1, 10, X)$$

- `1` → ainda é 1 frase (batch)
- `10` → ainda são 10 posições (palavras/tokens)
- `X` → **nova dimensão**, adicionada pela camada de embedding: os números que representam o significado de cada palavra naquela posição

## 3.3 A ideia central: mesma estrutura, valores diferentes

Isso é o ponto-chave. Todas as 10 linhas (palavras) **compartilham a mesma estrutura** — todas têm X colunas, e cada coluna "significa" o mesmo tipo de coisa entre uma palavra e outra (lembrando do tópico 1: esse "significado" da coluna é abstrato, aprendido no treinamento, não nomeável).

```
"o"        → [0.02, -0.11, 0.44, ..., 0.09]
"cachorro" → [0.12, -0.44, 0.03, ..., 0.91]
"correu"   → [0.55,  0.08, -0.29, ..., 0.14]
"muito"    → [-0.19, 0.33, 0.61, ..., 0.02]
              ↑col1   ↑col2  ↑col3        ↑colX
```

- **Coluna 1 pra "o"** e **coluna 1 pra "cachorro"** estão medindo *a mesma coisa* (seja lá o que o modelo aprendeu que aquela coluna captura) — só que com valores diferentes, porque "o" e "cachorro" são palavras muito diferentes.
- Isso é exatamente igual à analogia das coordenadas (tópico 1): se lat/long fosse a "estrutura" (coluna 1 = latitude, coluna 2 = longitude), toda cidade tem uma latitude e uma longitude — a estrutura é igual pra todas, mas o **valor** de cada cidade nessa estrutura é diferente, e é isso que diferencia uma cidade da outra.

## 3.4 Por que isso importa na prática

Esse tensor `(1, 10, X)` é exatamente o que alimenta as próximas camadas de um modelo tipo Transformer (BERT, GPT, etc.) — cada palavra chega como um vetor de significado individual, e as camadas seguintes (atenção, etc.) é que vão misturar informação **entre** essas linhas, pra que "banco" no contexto de "sentei no banco da praça" fique diferente de "banco" em "fui ao banco sacar dinheiro". Isso já é o próximo capítulo da história: embeddings contextuais.

## 3.5 Resumo do fluxo

```
Frase de texto
    ↓ tokenização
IDs de tokens          shape: (1, T)       T = número de tokens
    ↓ camada de embedding (lookup table)
Vetores de embedding    shape: (1, T, X)    X = dimensão do embedding
    ↓ (próximos capítulos: camadas de atenção, contexto, etc.)
```
